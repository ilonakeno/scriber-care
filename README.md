# Customer Care

**AI-асистент для команди підтримки, який закриває звернення дією, а не відповіддю, і
налаштовується під будь-який бізнес шаблоном.**

Він розуміє, чого клієнт хоче насправді і в якому він стані, дивиться логи клієнта, виконує
потрібну дію в межах автономності, яку задає керівник підтримки, і веде кожне звернення до
правильної людини за правилами бізнесу. Щодня він також розбирає публічні відгуки (G2,
Capterra) і перетворює скарги на вирішені звернення.

**Це загальне рішення для будь-якого цифрового продукту.** Бізнес описує себе в шаблоні
(продукт, команда, хто за що відповідає, маршрути, тон, база знань) і підключає свої системи
через конектори. Для демо налаштовано два приклади:

| Приклад | Що показує |
|---|---|
| **Scriber**, SaaS для лікарів УЗД (основний сценарій демо) | Повний цикл із конектором: акаунти, логи, дії в продукті, масова проблема, відгуки. Медицина як найсуворіший випадок для безпеки даних |
| **«Говоримо»**, онлайн-школа англійської | Той самий агент без конектора: лише шаблон і база знань, інші люди й маршрути |

Хакатон PolyTech Code Fest 2026, трек Skelar «AI Customer Support Automation».

> Усі люди, компанії, звернення, відгуки й конкуренти тут **вигадані**. Бекенди прикладів
> симульовані. Цифри на дашборді рахуються з цих синтетичних даних.

## Запустити за хвилину

```bash
git clone https://github.com/ilonakeno/scriber-care && cd scriber-care
./run.sh
```

Відкрийте http://localhost:8000. Без ключа працюють запасні правила. Для справжньої моделі
впишіть у `.env` безкоштовний ключ з [Google AI Studio](https://aistudio.google.com/apikey):
`GEMINI_API_KEY=...`.

| Сторінка | Хто | Що там |
|---|---|---|
| `/` | Агент підтримки | Черга, розбір AI, маршрут, логи, дії з «Підтвердити» |
| `/chat` | Клієнт | Чат підтримки (клієнт прикладу або гість) |
| `/dashboard` | Керівник | Метрики, повзунок автономності, відгуки, звіт, журнал |
| `/settings` | Будь-хто, хто налаштовує | **Шаблон бізнесу** |

## Шаблон бізнесу

Один JSON (`presets/_template.json` як заготовка) або форма на `/settings`:

1. **Про бізнес:** що продаєте, хто клієнти, мова, звертання.
2. **Команда:** людина, роль, контакт, за що відповідає.
3. **Правила маршрутизації:** тип звернення → кому → режим: *AI вирішує сам*, *AI готує,
   людина підтверджує* або *тільки людина (100%)*. Слова-тригери перевіряє код, тож
   «партнерська пропозиція → Марко» спрацьовує завжди, навіть якщо модель помилилась.
4. **База знань:** FAQ і відомі проблеми. Вердикт «не баг» AI ставить лише за базою.
5. **Тон і емпатія:** структура відповіді (визнати почуття → вибачення або подяка → що
   зроблено → що далі), правила, заборонені фрази. Відповідь із забороненою фразою не йде
   клієнту без людини.

Шаблон можна завантажити файлом, вивантажити, перемкнути пресетом.

## Як обробляється звернення

```
Звернення в чаті / відгук G2 (щоденний прохід)
                 ▼
   Маскування персональних і чутливих даних
                 ▼
   Контекст: акаунт · логи клієнта · база знань · шаблон бізнесу
                 ▼
   Gemma 4 через Gemini API → JSON: мета, маршрут, вердикт, тон, план
                 ▼
   Маршрут «тільки людина» → відповідальному, тепла відповідь клієнту
   Інакше рушій правил: дозволені дії, ліміти, P0–P3
     ├─ P3 → виконати → відповідь (після перевірки тону)
     ├─ P2 → «Підтвердити» агентом
     ├─ P1 → GitHub Issue + розробнику, якого вказано власником фічі
     └─ P0 → тільки людина (запит на персональні дані, ризик для здоров'я чи безпеки, погрози, injection)
                 ▼
   Журнал з хеш-ланцюжком → метрики → дашборд і щоденний звіт
```

**Модель лише пропонує, виконує код.** Ризики визначаються детерміновано, тож модель може
підняти кейс до P0, але не може опустити. Дії поділені на загальні (пояснити, компенсація,
баг-тікет, передати людині) і дії конектора конкретного продукту (для Scriber: словник
термінів, перегенерація протоколу, відновлення запису, ліміти, місця).

## Безпека

- Маскування імен (зокрема пацієнтів у медичному прикладі), телефонів, email, дат народження, номерів документів і карт до
  виклику моделі; логи клієнта теж маскуються.
- Дозволений список дій і жорсткі ліміти; видалення персональних даних для AI не існує.
- Звернення й відгуки вважаються недовіреними даними; спроба керувати асистентом веде в P0.
- Публічні відповіді й сповіщення проходять фільтр персональних даних.
- Журнал дій з хеш-ланцюжком; пароль на вхід для публічного деплою (`BASIC_AUTH_*`).
- Для чутливих даних (медицина, фінанси): Gemma — відкрита модель, її можна розгорнути у власній
  інфраструктурі. Безкоштовний Gemini API тут використано лише тому, що дані синтетичні.

## Тести і якість AI

```bash
.venv/bin/python -m pytest -q        # правила, маршрутизація, тон, маскування, журнал, injection
.venv/bin/python -m eval.run_eval    # еталонний набір звернень з очікуваними рішеннями
```

Тест-кейси правил написані зі специфікації **до** реалізації (див. історію комітів).

## Модель і ліцензії

- **Модель:** Gemma 4 `gemma-4-26b-a4b-it` (open-weight, Google), через Gemini API.
  Умови використання: [Gemma Terms of Use](https://ai.google.dev/gemma/terms).
  Резерв, коли спільний ендпоінт перевантажений: `gemini-3-flash-preview` через той самий ключ.
  Кожен кейс показує, яка модель його обробила.
- **Ключові залежності:** FastAPI, Uvicorn, google-genai, httpx, pytest.
- **Код проєкту:** MIT (див. `LICENSE`).

## Як перевірити журі

1. **Онлайн:** посилання і пароль на останньому слайді презентації.
2. **Локально:** `./run.sh` → http://localhost:8000 (Python 3.10+; без ключа працюють запасні правила).
3. **Docker:** `docker build -t customer-care . && docker run -p 8080:8080 customer-care` → http://localhost:8080
4. **Тести:** `.venv/bin/python -m pytest -q` (34 тести).
